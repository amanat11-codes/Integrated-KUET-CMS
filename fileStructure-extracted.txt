CMS Dummy Data File Structure
This document describes the binary files generated by main.c. It is intended for
collaborators who need to read or write the generated data.

Important format characteristics
  • Files are binary, not text or JSON.
  • Records are written directly with C fwrite():
     fwrite(&record, sizeof(record), 1, fp);
  • The format uses the compiler’s native struct layout, including alignment
    and padding bytes.
  • The current files were generated with a 64-bit MinGW GCC build on
    Windows. The current layout assumes:
        – char = 1 byte
        – int = 4 bytes
        – uint32_t = 4 bytes
        – float = 4 bytes, IEEE-754 representation
        – UserType enum = 4 bytes
        – little-endian byte order
  • Do not assume that a different compiler, architecture, or compiler packing
    option will produce the same offsets.
  • Strings are fixed-size character arrays. They are normally NUL-terminated
    and the unused bytes are zero-filled because the generator initializes structs
    with {0}. A string that exactly fills an array may not have a terminating
    NUL.
  • There is no magic number, version field, checksum, or schema identifier.
    Readers must already know which file type they are opening.
  • All offsets in this document are byte offsets from the beginning of the
    relevant file or struct and are zero-based.

credentials.dat
Record layout
credentials.dat is a sequence of 21 User records. Each record is 24 bytes,
so the file size is currently 21 * 24 = 504 bytes.
typedef struct {
    char id[9];
    char pass[9];
    UserType userType;
} User;

           Offset   Size    Field          Notes
               0      9     id             Up to 8 characters plus NUL
               9      9     pass           Up to 8 characters plus NUL
              18      2     padding        Alignment before userType
              20      4     userType       Values 1, 2, or 3


To read record number n (zero-based), seek to:
record_offset = n * 24
Records are written in this order:
  1. Students 52501001 through 52510010
  2. Teachers 10000001 through 10000010
  3. Administrator 00000000
The first student and first teacher use password 00000000. Other generated
passwords are eight-character numeric strings and are regenerated randomly
each time the generator runs.

Teacher files
Each TEACHER_ID.teacher file contains a TeacherFileHeader, one
TeacherProfile record, and a counted list of taught course names. The
course names are stored in the same form used by the roster filenames, such as

MATH 1101. Teacher IDs use the same eight-digit format as student IDs. The
file name must match the teacherId field: for example, 10000001.teacher
contains the record whose teacherId is 10000001. The generated email address
follows last_name@dept_short_code.kuet.ac.bd, and phone numbers use
Bangladesh’s 01XXXXXXXXX format.

    uint32_t teacherProfileOffset;
    uint32_t taughtCoursesOffset;

    char name[80];

typedef struct {
    char courseName[12];

The header is 12 bytes, TeacherProfile is 415 bytes, and each TaughtCourse
is 12 bytes. The current file has three course entries, so its total size is 463
bytes. All fields are fixed-size, NUL-terminated character arrays and have no
internal alignment padding.

Course roster files
Each COURSE_NAME.course file contains a CourseFileHeader followed by one
CourseEnrollment for every student who took the course. For example, MATH
1101.course contains the ten generated student IDs, while CSE 1109.course
contains the generated CSE student ID.

typedef struct {
    char studentId[9];
} CourseEnrollment;
The header is 4 bytes and each enrollment is 9 bytes, so the current roster
files are 94 bytes for common courses and 13 bytes for department-specific
courses. The roster deliberately stores no marks. To update marks, read the
roster IDs, open each corresponding .student file, locate the matching course
in AcademicRecord.courses, and update that Course record and the derived
GPA values. This keeps student files as the single source of truth for marks.

Notice files
Each file named NNNN.notice contains exactly one Notice struct. For example,
0001.notice contains notice ID 0001.
typedef struct {
    char noticeId[5];
    Date date;
    char Title[100];
    char Description[512];
} Notice;
Current size: 632 bytes.

            Offset   Size    Field             Notes
                 0      5    noticeId          Four-digit ID plus NUL
                 5      3    padding           Alignment before Date
                 8     12    date              Date struct
                20    100    Title             Full notice title
               120    512    Description       Full notice description


There is no collection file for notices. To read all notices, enumerate the *.notice
files and read one Notice record from each file.

Reading and writing recommendations
Reading in C with the same layout
The safest option for the current format is to compile against the same struct
definitions and read the complete record:
StudentFileHeader header;
StudentProfile profile;
AcademicRecord academic;
HallDetails hall;
LibraryDetails library;

fread(&header, sizeof(header), 1, fp);


                                        10
fseek(fp, (long) header.studentProfileOffset, SEEK_SET);
fread(&profile, sizeof(profile), 1, fp);
fseek(fp, (long) header.academicRecordOffset, SEEK_SET);
fread(&academic, sizeof(academic), 1, fp);
fseek(fp, (long) header.hallDetailsOffset, SEEK_SET);
fread(&hall, sizeof(hall), 1, fp);
fseek(fp, (long) header.libraryDetailsOffset, SEEK_SET);
fread(&library, sizeof(library), 1, fp);
Production code should check every fread() result and validate offsets against
the file size before seeking.

Writing records
  • Preserve the exact field widths and record order.
  • For a .student file, write a 16-byte header first, then StudentProfile,
    AcademicRecord, HallDetails, and LibraryDetails.
  • For a .teacher file, write a TeacherFileHeader, one TeacherProfile,
    and the number of TaughtCourse records specified by the header.
  • For a .course file, write a CourseFileHeader followed by exactly
    studentCount CourseEnrollment records.
  • Zero-initialize structs before assigning fields.
  • Do not write pointers, dynamically allocated strings, or sizeof(pointer).
  • Do not add, remove, or reorder fields without regenerating all existing files.
  • Use snprintf() or equivalent bounded copying for fixed-size strings.
  • A fixed-size string occupies its complete field width. Encode text as bytes,
    truncate to at most field_width - 1 bytes, and append NUL bytes to
    fill the field. Do not write a length prefix.
  • Keep bookCount in the range 0..3.
  • Keep UserType values within the documented enum values.
  • Write integers as signed or unsigned 4-byte little-endian values as appro-
    priate, and floats as 4-byte little-endian IEEE-754 values.
  • Include every documented padding byte when constructing a file manually.

Cross-language readers
A Python, Java, Rust, or other non-C reader should parse each field manually
using the documented offsets, fixed widths, little-endian integers, and little-
endian IEEE-754 floats. It should not assume that a language’s default struct
unpacking matches C padding.
For example, these Python struct format fragments describe the current layout.
The explicit < selects little-endian encoding and standard sizes; the x entries
represent C alignment or trailing padding:
import struct

HEADER = struct.Struct("<4I")                           # 16 bytes


                                       11
COURSE = struct.Struct("<5s12s30sxff3sx")    # 60 bytes
ACADEMIC_PREFIX = struct.Struct("<80si50s10sii4f") # 168 bytes
HALL = struct.Struct("<50s2xii10s2x12si11s11s2x") # 112 bytes
ISSUED_BOOK = struct.Struct("<80s12s")       # 92 bytes
LIBRARY_HEADER = struct.Struct("<i")         # followed by 3 ISSUED_BOOK values
TEACHER_HEADER = struct.Struct("<3I")       # 12 bytes
TEACHER = struct.Struct("<80s9s20s50s16s80s160s") # 415 bytes
TAUGHT_COURSE = struct.Struct("<12s")       # 12 bytes
COURSE_HEADER = struct.Struct("<I")         # 4 bytes
COURSE_ENROLLMENT = struct.Struct("<9s")    # 9 bytes
Write bookCount with LIBRARY_HEADER and then pack three ISSUED_BOOK values.
Likewise, pack the academic prefix followed by eight COURSE values. A portable
writer should assert the resulting lengths:
assert HEADER.size == 16
assert COURSE.size == 60
assert HALL.size == 112
assert TEACHER_HEADER.size == 12
assert TEACHER.size == 415
assert TAUGHT_COURSE.size == 12
assert COURSE_HEADER.size == 4
assert COURSE_ENROLLMENT.size == 9
When creating a student file, calculate the four header offsets from the actual
serialized block lengths:
profile_offset = HEADER.size
academic_offset = profile_offset + len(profile_bytes)
hall_offset = academic_offset + len(academic_bytes)
library_offset = hall_offset + len(hall_bytes)
header = HEADER.pack(profile_offset, academic_offset,
                     hall_offset, library_offset)
student_bytes = header + profile_bytes + academic_bytes + hall_bytes + library_bytes
The snippets are layout guidance, not a complete validation library. Check that
every string fits, IDs match their filenames, offsets are in increasing order, and
the final file length is exactly the expected end offset.
For long-term compatibility, consider changing the format to an explicitly ver-
sioned format with fixed-width integer types, defined endianness, and a serializa-
tion specification. The current format is suitable for tightly controlled builds
but is not portable by itself.
